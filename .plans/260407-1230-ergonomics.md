
# Ergonomics

Some early feedback for component playground:
- Working with `add_`, `addWhen_` etc is difficult.
- `Component_` still carries `msg` — is it needed?

## Completed

### Remove `msg` from `Frame` / `Playground`

`Frame` and `Playground` had a `msg` type parameter that only existed for
`StaticFrame`. Interactive frames were already type-erased to `Update t e`.

- Changed `StaticFrame (Html msg)` → `StaticFrame (Html (List e))`
- Removed `msg` from `Frame e t msg` → `Frame e t` and `Playground e t msg` → `Playground e t`
- `processFrame` maps `List e` → `Update t e` via `Update [] effects`
- Updated all signatures in Component.elm, Application.elm, examples, and tests
- Also fixed pre-existing test bug: `val` → `value` field name in `ControlTests.elm` maybe tests

## Steps

### Step 1 — Explore whether `Component_` still needs `msg`

`Component_ e t i m msg` stores `view : i -> m -> (i -> msg) -> View msg`. The
`msg` only matters because the view receives a setter `(i -> msg)`. But `explore`
already constrains `msg ~ Update t e`, and `example` does the same.

Questions to answer:
- Is there a use case where `msg` is something other than `Update t e`?
- Could the setter be internalised so the view just returns `View (Update t e)`
  directly, eliminating `msg` from `Component_` entirely?
- What impact would that have on the user-facing API (`component`, `component_`,
  `componentWithPortals`, `componentWithPortals_`)?

### Step 2 — Revisit `add_`, `addWhen_`

Was thinking it would be great to have `Control_ e t state value`
and then `add_` taking the `{ state : state, valueF : state -> value }`.

I found myself tripping over type errors, particularly with `add_` providing
two parameters — getting them in the wrong order etc.
